## What

Brings the Expo app's **Home** and **Communities** surfaces up to web parity, and fixes the reason message reactions could never be given from mobile.

Everything here lives in `expo-app-standalone 3/` — no web or API behaviour changes.

---

## 1. Design system on mobile (dark page background)

The mobile palette was a hand-copied subset of the web tokens, and it had drifted: dark `mutedForeground`/`foregroundSoft` were the light values, and the semantic names the web uses (`backgroundSubtle`, `surfaceHover`, `borderSubtle`, `overlay*`, `--like`) did not exist at all.

- **`constants/designSystem.ts` (new)** — the primitive Geist scales plus the semantic light/dark themes, lifted from `packages/design-system` and `apps/web/app/globals.css`, with the radius scale, RN elevation descriptors, and the chat name-colour rotation.
- **`constants/colors.ts`** — now derives both palettes from those themes. The web names are the real tokens; the old mobile names (`card`, `primary`, `mutedForeground`, `subtle`…) are kept as aliases so no screen had to change to keep working.
- **`hooks/useColors.ts`** — resolves to the **dark** palette by default, because the web app is dark-only (`colorScheme: "dark"` in the root metadata); a light-mode phone must not see a different product. `useColors()` also returns the resolved `scheme`/`isDark`, and every screen that styled its status bar from the *device* scheme now styles it from the tokens it actually rendered with. `EXPO_PUBLIC_COLOR_SCHEME=light` opts a build back into the platform scheme.
- **Page background** — screens were painting the *sidebar* colour (`#0E0E10`) as the page. Roots, headers and the tab bar now use `--color-background` (`#09090B`), matching the web. The community list rows were also filling themselves with that sidebar colour, which is what left a lighter grey band down the middle of the Communities tab; the rows are now transparent over the page and lift onto the raised surface when pressed, like the web sidebar rows. The header's icon button got the same treatment — its pressed state had become invisible once header and page shared a colour.
- **`app.json`** — `userInterfaceStyle: "dark"` so native chrome (keyboard, alerts, switches) matches.

## 2. Message reactions were silently rejected (the reported bug)

`toggleReaction()` posted `{ emoji }`, but the reactions endpoint takes an explicit desired state — `{ desiredEmoji }` (string or `null`) — and answers **HTTP 422** for anything else. The mobile client swallowed the error in an empty `catch`, so tapping a reaction did nothing at all.

- `setMessageReaction(communityId, messageId, desiredEmoji)` replaces it, and the handler now mirrors the web client: **tapping your own reaction removes it, any other tap replaces it**, the pill flips optimistically, and the server's grouped reactions are the final word (with a rollback if the write fails).
- The desired state is also tracked in a ref, because two taps in the same tick would both read a stale message and the second would repeat the first intent instead of undoing it.
- The reaction helpers (`myReactionEmoji`, `applyReactionInsert/Delete`, `projectOwnReaction`, `nextReactionIntent`) are ports of the web cache helpers, so both clients project the same state.

## 3. The comment section, on every content type

The mobile cards showed a comment *count* that did nothing when tapped. The web `CommentSection` is now ported:

- **`lib/comments.ts` (new)** — `getComments` / `postComment` / `deleteComment` / `toggleCommentReaction` for threads, showcase, resources and events. It absorbs the three ways those routes differ: nested vs. flat lists (events return flat), per-kind body limits (showcase 1000 / events 2000 / others 5000), and comment reactions existing **only on threads**.
- **`components/community/CommentsSheet.tsx` (new)** — composer, live count, Most recent / Most popular sort, the timeline treatment, one level of nested replies with collapse/expand, an inline reply composer seeded with `@Name `, delete for your own comments, and the five allowed emoji reactions on threads.
- Cards and the detail view open it, and the card's comment count updates as you post and delete.

## 4. Likes, saves and RSVPs unified

The four content APIs spell the same three interactions differently (`count` vs `like_count` vs `save_count`, `liked` vs `saved` vs `bookmarked`, and showcase's generic `{ action, active }`). One table in `useContentActions` reconciles them, so:

- every interaction is now an **explicit desired state** through `setContentAction` (never a toggle),
- rapid taps are coalesced by the existing `BooleanIntentCoalescer`,
- the heart picks up the web `--like` pink, other actions light up in the accent colour, count-less saves toggle "Save"/"Unsave", and RSVPs read "3 going",
- the community is read from the item, which is what lets the home feed mix posts from many communities in one list.

## 5. Showcase tab + create/edit

- The community tab bar now matches the web's order and set (Chat · Threads · Showcase · Resources · Events). Showcase follows its own `showcase_enabled` flag and defaults to on — the same rule as the web `areas.ts`, so a community row that predates the flag still shows it.
- The composer supports showcase create/edit: title, up to 5 uploaded images, category chips, reply and visibility toggles. Uploads reuse the per-kind `/upload` contract, and images are converted by the app's existing WebP prep pipeline.
- Showcase has no community-scoped realtime room on the web (its room is keyed by *post* id), so that tab stays fresh through the foreground refetch and pull-to-refresh instead — noted in the hook.

## 6. Home feed

`/api/home/feed` is now rendered instead of "Home — coming soon":

- cross-community cards (threads, events, resources, showcase) with a chip naming the community each post came from,
- working like/save/RSVP from the feed,
- tap-through to the full post detail, and the same comment sheet,
- keyset pagination (`?before=<created_at>`), pull-to-refresh and an empty state.

The card, the detail view and the interaction state were extracted into `components/community/contentView.tsx`, so a post behaves identically in the feed and in its community tab — one implementation, not two.

## 7. Card layout matched to the web cards

- **The category/type pill is gone.** On the web the category is the muted second line of the author meta — "Threads · Discussion", "Resources · Figma", "Event · Online", "Showcase · UI Design" — so the card now renders exactly that (and the hashtag pills went with it; the web cards never render them).
- **Save moved into the ··· menu**, where the web keeps it: it is available to everyone (Save/Unsave), with Edit and Delete below it for the author. The footer is back to the web's two affordances — the heart with its count and the comment count. Events keep their RSVP in the footer, standing in for the web's wide "I'm Going" call-to-action.
- **"Read more" on long bodies**, following the web rule: a thread collapses at 2 lines as soon as it has an attachment (5 when it is text-only), an event's description collapses at 2, and a resource's body is clamped to 3 with no affordance. Showcase titles are never clamped, as on the web.
- **The community attribution moved to the bottom-right of the card**, where the web cards put it (`CommunityPostLabel`): the feed used to open each card with a community avatar + name row, which no web card does. The footer is now the web's shape — heart and comment count on the left, "posted in ⊙ <community>" right-aligned and truncating.
- The author line is the web `PostAuthorMeta` layout: name plus relative date on one line, the category label beneath.
- **No divider above the footer.** The card ran a hairline between the body and the engagement row; the web cards run the footer straight off the body (`mt-3`, spacing only), so the hairline is gone and the row spacing is the web's `gap-4`.
- **The like button is now the web heart.** It was a Feather outline tinted pink, which read as an outline even when liked; it is now the web `HeartIcon` — the same `0 0 16 16` path, filled with the like pink (`--like`, #F91880) stroke *and* fill when active, muted foreground when not, plus the web's quick pop (1 → 1.32 → 0.94 → 1, skipped under reduced motion). Applies to threads, resources, events, showcase and the detail view; the chat love reaction already used the web's red-500 picker colour.

## 8. Haptics

`lib/haptics.ts` (new) is one semantic vocabulary over two engines: iOS gets the `UIFeedbackGenerator` styles, Android gets the platform's own haptics constants (`performAndroidHapticsAsync`, which does not need `VIBRATE` and is Android's recommended API — the plain `Vibrator` these calls would otherwise fall back to only simulates them).

- `hapticImpact()` — a long press that opens a sheet (medium / `LONG_PRESS`).
- `hapticSelection()` — moving between choices: a menu row, a sort chip, a comment control (selection / `SEGMENT_TICK`).
- `hapticToggle(active)` — a switch flipped: liked ↔ unliked, reacted ↔ not (light / `TOGGLE_ON`·`TOGGLE_OFF`).
- `hapticSuccess()` / `hapticError()` — a write landed or rolled back (success/error / `CONFIRM`·`REJECT`).

Wired through: the message action sheet opens on a long press and ticks on every row; reaction ticks fire from the single reaction funnel, so the pill on a bubble and the tile in the sheet feel identical; the card footer's heart/RSVP/save tick in the direction of the tap; the post options menu, the comment sheet's sort chips, reply/collapse controls, its reaction picker and the emoji pills all tick; posting a comment confirms and a failed write rejects. Every call is fire-and-forget — a device with no haptic engine rejects the promise, and a haptic is never worth taking a gesture down for.

## Not included

- **Members tab** (web has members/roles/invite) — next milestone.
- **Video uploads in showcase** — the web uses a presigned R2 direct-upload ticket; mobile posts images through the proxy path for now.
- Create/edit is deliberately not offered from the home feed, where the post's community membership isn't known; it stays on the post's community tab.

## Verification

- `npm run typecheck` in `expo-app-standalone 3` (`tsc --noEmit`) — clean.
- `Community`, `CommunityContent` and the feed types were reconciled against the four API routes and their handlers (`like`/`save`/`rsvp`/`bookmark`/`reactions`/`comments`) before wiring, and the reaction fix is against the route's own 422 message.
- No web, realtime or schema files are touched.
